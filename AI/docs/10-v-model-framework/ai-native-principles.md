# AI Native 原则

## 1. 人工批准是边界

AI 可以起草、评审、总结和比较，但不能把建议自动变成正式交付物。

推荐状态：

| 状态             | 含义          |
| -------------- | ----------- |
| AI Draft       | AI 生成或修改的草案 |
| Human Reviewed | 责任人已经审查     |
| Approved       | 已进入正式基线     |

## 2. 追踪关系优先

AI 的价值高度依赖上下文连接能力。需求、设计、实现、测试、缺陷和发布判断之间越清晰，AI 越能做出可靠的分析。

推荐 ID 类型：

| 交付物 | 示例 ID |
| --- | --- |
| 需求 | `REQ-001` |
| 基本设计项 | `BD-001` |
| 详细设计项 | `DD-001` |
| 测试用例 | `TC-001` |
| 缺陷 | `BUG-001` |
| 架构或设计决策 | `ADR-001` |

## 3. AI 输出必须被度量

AI Native 工程不能只靠主观感觉判断“好像有用”。需要把 AI 带来的质量、效率和风险变化量化。

可用指标：

- 需求歧义检出数。
- 评审缺陷检出率。
- 追踪关系覆盖率。
- 测试观点覆盖率。
- AI 生成测试用例采纳率。
- 缺陷逃逸率。
- 返工周期。
- 变更影响分析准确率。

## 4. 保密边界要显式化

通信、计费、账务等系统往往涉及敏感业务信息。知识库应该把流程知识和受保护的项目数据分开。

推荐数据分级：

| 数据级别 | 说明 | AI 使用原则 |
| --- | --- | --- |
| 公开流程知识 | 通用工程方法、公开模板 | 可用于通用 AI |
| 内部流程知识 | 公司内部模板、流程规范 | 使用批准的内部工具 |
| 项目机密数据 | 客户、合同、系统、业务细节 | 严格权限控制 |
| 生产数据 | 日志、个人信息、账务数据、故障数据 | 脱敏和审批后使用 |

## 5. AI 应嵌入评审关口

AI 的位置不应该只在写文档时，而应该进入每个关键评审点。

典型能力：

- 需求评审助手。
- 设计一致性检查器。
- 测试覆盖检查器。
- 变更影响分析器。
- 缺陷根因总结器。
- 发布风险总结器。
